# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

## What this is

themovie: a subscription SaaS where students go script → storyboard → rendered clips using AI generation. Next.js 16 (App Router) + Supabase (Postgres/Auth/Realtime/Storage) + Vercel AI SDK + BytePlus ModelArk (Seedream image / Seedance video).

**Next.js 16 breaking changes that matter here** (see AGENTS.md — don't rely on training-data Next.js knowledge):
- Middleware is renamed to **Proxy**: the file is `src/proxy.ts` exporting `proxy()`, not `middleware.ts`/`middleware()`. Docs at `node_modules/next/dist/docs/01-app/01-getting-started/16-proxy.md`.
- Check `node_modules/next/dist/docs/` before using any App Router API you're not certain about for this version (16.2.11).
- The proxy matcher in `src/proxy.ts` excludes `.well-known/workflow` in addition to the usual static-asset paths — that's the Vercel Workflow DevKit's internal callback route, and it must stay unauthenticated/unredirected or workflow step callbacks break.

## Commands

```bash
npm run dev      # start dev server (localhost:3000)
npm run build    # production build
npm run start    # run production build
npm run lint     # eslint (flat config, eslint.config.mjs)
```

No test runner is configured in this repo yet.

Supabase (local CLI, `supabase` is a devDependency):
```bash
npx supabase migration new <name>   # create a new migration under supabase/migrations/
npx supabase db push                # apply migrations to the linked project
```
Migrations are the only source of schema truth — there is no ORM.

## Architecture

**Provider abstraction (`src/lib/providers/{llm,image,video,billing}/`)**: every external capability is accessed through an interface (`LLMProvider`, `ImageProvider`, `VideoProvider`, `BillingProvider`) with up to three implementations, and `index.ts` in each folder picks the first adapter whose env var is set, in a fixed priority order, falling back to mock — so **local dev missing every real key silently runs on mocks**. The concrete adapter set differs per capability, so don't assume BytePlus is universal:
- `image/` and `video/`: `byteplus-adapter.ts` (real calls to BytePlus ModelArk, `BYTEPLUS_API_KEY`) → `gateway-adapter.ts` (Vercel AI SDK / `AI_GATEWAY_API_KEY`) → `mock-adapter.ts`.
- `llm/` (script generation/breakdown/enhancement): `deepseek-adapter.ts` (`DEEPSEEK_API_KEY`, via `@ai-sdk/deepseek` direct, not Gateway) → `gateway-adapter.ts` → `mock-adapter.ts`. There is no BytePlus LLM adapter.
- `billing/`: `stripe-adapter.ts` (`STRIPE_SECRET_KEY`) → `mock-adapter.ts`. No Gateway variant — billing isn't an AI capability, so `getBillingProvider()` only has two rungs.

`src/lib/providers/byteplus/client.ts` is a thin authenticated `fetch` wrapper (plain fetch, not routed through the AI SDK/Gateway); `src/lib/providers/byteplus/model-limits.ts` maps the configured `BYTEPLUS_VIDEO_MODEL` to its valid duration range so UI controls don't hardcode limits. When adding a new generation capability, follow this same adapter-per-provider pattern rather than calling an SDK directly from a server action.

`ImageProvider.generateImage` returns `{ images: GeneratedImage[] }` (always an array, even for one image) — batch generation is first-class; BytePlus can legitimately return fewer images than requested (`quantity`), and callers must reconcile that against however many ledger rows they pre-created. `VideoProvider` has **no single blocking "generate" call** — `startVideoTask(input)` registers a task and returns a handle, `pollVideoTask(handle)` reports `queued|running|succeeded|failed|cancelled|expired`. This matches BytePlus's real async create+poll API; the mock/gateway adapters resolve on the first poll (gateway does the blocking Veo call inside `startVideoTask` and stashes the result on the handle) so nothing else needs to know which adapter is active.

**Generation ledger pattern**: any code path that calls an external generation provider must insert a `pending` row into `generations` *before* invoking the provider, then update that row to `succeeded`/`failed` afterward — never call a provider without a ledger row bracketing it. There are two accepted ways to bracket the call, pick based on expected duration:
- **In-request, via `after()`** — for calls short enough to not need durability/retries. See `src/lib/actions/generations.ts:generateShotImage`: it inserts the pending row and flips the shot to `generating` in the request/response cycle, then does the actual provider call inside `after()` (runs post-response) using a fresh Supabase client (the request-scoped client's cookie store isn't valid anymore once the response has been sent). `src/lib/actions/media.ts:generateFreeformImages`/`generateCharacterSheet` follow the same shape but insert **one row per requested image**, all sharing a `batch_id`, and pair the provider's returned `images[]` to those rows positionally in `settleImageBatch`.
- **Durable, via Vercel Workflow DevKit (`workflow` package)** — for longer/flakier calls that need automatic retries and to survive past a single request lifecycle. See `src/lib/actions/generations.ts:generateShotVideo` / `src/lib/actions/media.ts:generateVideoFromImage` + `src/lib/workflows/generate-video.ts`: the action inserts the pending row, then calls `start()` from `workflow/api` to kick off a `"use workflow"` function and immediately returns (never awaits the generation). Inside the workflow: a `startVideoTask` step registers the task (`FatalError` for `NoVideoGeneratedError`, `RetryableError` otherwise); a `pollVideoTask` step calls the provider's poll method and — while still `queued`/`running` — throws `RetryableError` with an escalating `retryAfter` (`getStepMetadata().attempt` drives the backoff schedule), which is how the poll loop itself is implemented: Workflow's own retry scheduler re-invokes the step, no manual sleep loop, and it survives a server restart mid-poll. The workflow run id is stored on `generations.workflow_run_id` for tracing (`npx workflow inspect run <id>`).

Steps run via Workflow's internal callback, not a continuation of the original request, so they have no session cookie — they must use `src/lib/supabase/service.ts` (service-role key, bypasses RLS) instead of the cookie-based client. This is safe only because the Server Action already validated ownership before calling `start()`; never import `service.ts` from a Server Component/Action handling a live user request. **`service.ts` requires `SUPABASE_SECRET_KEY`** — without it, `persistOutcome` throws `supabaseKey is required` and the generation row is stuck at `pending`/`generating` forever (the workflow has no fallback path if the persist step itself fails). Set this env var before expecting any video generation, mock or real, to reach a terminal state.

Video generation can run past Node's default fetch timeout, so `src/instrumentation.ts` registers a global AI Gateway provider with an extended-timeout Undici dispatcher (15 min) — this only applies to the Gateway/Veo path. BytePlus calls (`byteplus/client.ts`) are plain `fetch` with no extended timeout, deliberately: every individual BytePlus HTTP call (create task, each poll) is short; overall video generation time is handled by the poll/retry loop above, not by one long-lived request.

**Terminal media URLs are always our own Storage URLs, never a raw provider URL.** BytePlus image links expire in 24h; nothing should persist one as permanent. `src/lib/media/copy-to-storage.ts:copyToMediaBucket()` downloads a provider URL (or a mock adapter's `data:` URI) and re-uploads it into the private `media` Storage bucket, returning `{ path, signedUrl }` (1h TTL) — every code path that marks a generation `succeeded` calls this first and writes both `output_url: signedUrl` and `storage_path: path`. `storage_path` (on both `generations` and `asset_images`) is the durable column — display code re-derives a fresh signed URL from it on read (`supabase.storage.from("media").createSignedUrl(storagePath, ...)`, see `generation-media.tsx`). `output_url` is a display cache only, not authoritative: an earlier version of this codebase persisted the 1h signed URL into `output_url` as if it were permanent, which silently broke any media viewed more than an hour after generation — `generations.storage_path` (`20260808130234_add_generations_storage_path.sql` + a backfill migration) exists specifically to fix that. When touching generation-display code, always resolve the URL from `storage_path`, never trust a stored `output_url` to still be valid.

**Data model / ownership chain**: `projects (user_id)` → `scenes (project_id)` → `shots (scene_id)` → `generations`, plus `assets (project_id)` → `asset_images (asset_id)`, `uploads (project_id)`, and the join tables `shot_assets (shot_id, asset_id)` / `scene_assets (scene_id, asset_id, wardrobe_note)` linking characters/locations/props to the shots/scenes they appear in. `generations.project_id` is a **deliberately denormalized** required column (not just derivable via `shot_id → scenes → projects`): every non-shot generation (`kind` = `freeform_image`/`image_to_video`/`upload_to_video`/`character_sheet`/`scene_storyboard`) has no shot at all, so a first-class `project_id` on every row keeps both RLS and the "All Media" realtime filter a single join/predicate instead of branching by kind. `generations.kind` constrains which of `shot_id`/`scene_id` a row *may* carry (`kind='shot'` → may carry `shot_id`, never `scene_id`; `kind='scene_storyboard'` → may carry `scene_id`, never `shot_id`; every other kind carries neither) — but neither FK requires the id to be *present*: both are `on delete set null`, not cascade, specifically so that regenerating a project's scene breakdown (which deletes and reinserts every scene/shot) orphans old scene/shot-linked generations instead of destroying them — they stay fully visible (e.g. in All Media, which only ever filters by `project_id`) with a null scene_id/shot_id rather than being deleted. (This was a real bug, not a preemptive design: `20260809171750_preserve_generations_on_scene_shot_delete.sql` fixed both FKs from `on delete cascade`, which was silently destroying already-generated, BytePlus-billed media — row and Storage file — every time a breakdown was regenerated.) Don't confuse `kind` with the separate `type` column (`'image' | 'video'`, media modality) — `kind` categorizes *why* the row exists (`shot`/`freeform_image`/`image_to_video`/`upload_to_video`/`character_sheet`/`scene_storyboard`), `type` categorizes *what* the provider produced; both are set on every insert. `generations.asset_id` tags character-sheet generations (and anything else that references a character); `generations.batch_id` groups the rows produced by one "generate N images" request; `generations.params jsonb` carries the request shape (prompt/size/duration/reference ids/etc.) that doesn't need its own column. `assets.reference_image_url` and `asset_images.label` — a saved reference image can carry a display label (e.g. "Hospital gown") so a generation can target a specific outfit/variant instead of always resolving to the primary image; it's display text only, not an identity key.

`projects` and the billing tables (`subscriptions`, `credits_ledger` — see below) are the only tables with a `user_id` column; every other table under the project hierarchy enforces ownership via RLS policies that join back up the chain to `projects.user_id` (see the `exists (select 1 from ... join ...)` policies in the `supabase/migrations/*.sql` files). When adding a table under this hierarchy, follow the same join-based RLS pattern rather than adding a redundant `user_id` column.

**Billing & credits** (`subscriptions`, `credits_ledger`, `src/lib/billing/`, `src/lib/providers/billing/`, `src/app/api/webhooks/stripe/route.ts`): one `subscriptions` row per user carries plan, Stripe identifiers, and a cached `credit_balance`; `credits_ledger` is an append-only audit trail (positive = grant, negative = spend) with a Postgres trigger (`apply_credit_ledger_entry`) that keeps `credit_balance` in sync atomically on every insert — so "can this user afford a generation?" is always a single indexed read, never a summed history. Neither table has an authenticated-role write policy; every write goes through the service-role client (`spend-credits.ts`, the Stripe webhook), the same "trusted server code, no user session" pattern as the video workflow. `src/lib/billing/spend-credits.ts` has two calls, used together but never merged: `requireCredits(userId, cost)` gates *before* a generation's pending ledger row is created (so an unaffordable request never leaves a stray `pending` generation behind), and `recordSpend(...)` only runs once a generation is confirmed `succeeded` — a failed generation never costs a credit and needs no compensating refund. The Stripe webhook route is the one deliberate exception to "server actions are the only way the UI mutates data" (Stripe calls over HTTP; it can't invoke a Next.js server action) and is only reachable once `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET` are set — the mock billing adapter instead writes `subscriptions`/`credits_ledger` synchronously inside `startCheckout` and never hits this route. Webhook idempotency (Stripe retries deliveries at-least-once) is enforced by a real constraint, not application logic: `credits_ledger.stripe_event_id` has a unique partial index, so a replayed event's insert hits Postgres error `23505` (`isDuplicateEventError` in the webhook route), which is treated as "already applied." `src/lib/billing/plans.ts` (plan catalog/pricing) and `credit-costs.ts` (per-generation credit cost, image flat rate + video scaled by duration × resolution) hold placeholder numbers deliberately kept separate from the mechanism above — tune the numbers without touching the ledger/gating code.

**Storage**: one private bucket, `media`, path-prefixed `<project_id>/{generations,characters,uploads}/...`; `storage.objects` RLS resolves `(storage.foldername(name))[1]` against owned projects (see the bottom of `20260728230422_phase5_media_studio.sql`). Never make this bucket public — always read via `createSignedUrl`.

**Realtime**: tables whose rows need to be pushed to the client must be added to the `supabase_realtime` publication in a migration (see the bottom of `20260725190000_phase3_generations.sql`). `generations` also has `replica identity full` set (`20260808153222_set_generations_replica_identity_full.sql`) — Realtime's `postgres_changes` filter (e.g. `project_id=eq.<id>`) is evaluated against the row payload it receives, and the default replica identity only includes the primary key on DELETE, so without `full` a delete event's payload has no `project_id` for the filter to match against and the event silently never reaches subscribed clients; `subscriptions` doesn't need this since nothing subscribes to its deletes. `generations` and `subscriptions` are the only published tables (`subscriptions` added by `20260809214835_add_subscriptions_realtime.sql`, for `credit-balance.tsx`'s live balance indicator); asset/upload/character CRUD is refreshed via `revalidatePath`/full reload instead, not realtime. Project-scoped UI (`src/app/projects/[id]/_components/generation-feed.tsx`, used by the Images/Videos/Media/Characters tabs) subscribes filtered by `project_id=eq.<id>` and further filters by `kind`/`asset_id` client-side, since Supabase Realtime's filter string only expresses one condition; `credit-balance.tsx` similarly filters `subscriptions` by `user_id=eq.<id>`. Both follow the same required ordering: `await supabase.auth.getSession()` and `supabase.realtime.setAuth(token)` **before** `.channel(...).subscribe()` — RLS on these tables is keyed off `auth.uid()`, so if the channel joins before the socket has the user's JWT, every event is silently invisible under RLS for that channel's entire lifetime (no error, it just never fires). Known rough edge in this Next.js 16/Turbopack dev setup: `router.refresh()` called after a directly-invoked (non-`<form action>`) Server Action has been observed to hang silently (no thrown error) rather than complete — `src/app/projects/[id]/images/image-generate-form.tsx`'s upload mode and `delete-upload-button.tsx` use `window.location.reload()` instead, which has proven reliable. Prefer realtime subscriptions over `router.refresh()` for reflecting server-action results in an already-mounted client component; reach for a full reload only where realtime isn't available (tables outside `generations`/`subscriptions`).

**Auth**: Supabase SSR auth via `@supabase/ssr`. Four separate client constructors, each for a different context — do not cross-use them:
- `src/lib/supabase/server.ts` — Server Components/Actions (cookie read, best-effort write).
- `src/lib/supabase/client.ts` — Client Components.
- `src/lib/supabase/middleware.ts` — used from `src/proxy.ts`; refreshes the session on every request and redirects unauthenticated users away from non-`/login`, `/signup`, `/auth` routes. The comment above `getClaims()` in that file matters: never insert an early return between `createServerClient()` and `getClaims()`, or the refreshed session cookie is silently dropped.
- `src/lib/supabase/service.ts` — service-role client for use only inside Workflow `"use step"` functions (or other detached background execution) that have no request cookie to read; bypasses RLS, so never use it on a live user request path.

**Server actions** (`src/lib/actions/*.ts`) are the only way the UI mutates data — no route handlers/API routes for CRUD. Each checks `auth.getUser()` itself (RLS is the backstop, not the only check) and calls `revalidatePath` on affected routes (except the generation actions, which rely on the `generations` realtime subscription instead — see above). `src/lib/actions/project-guard.ts:loadOwnedProject()` is the shared auth+ownership check used by every project-scoped action file (`media.ts`, `assets.ts`, `uploads.ts`); `generations.ts` keeps its own shot-scoped `loadShotForGeneration()` since it additionally validates a shot's prompt/status.

**Project workspace IA**: `src/app/projects/[id]/layout.tsx` renders a persistent left sidebar (`_components/side-nav.tsx` — project title, style selector, live credit balance, nav links) shared by every sub-route — individual pages under `[id]/` render only their own `<main>`, not page-level chrome. Nav items: Script (`page.tsx`, project settings/script), All Media (`media/`), Generate Scenes (`scenes/`), Images (`images/`, freeform text-to-image with batch quantity + character reference; `image-generate-form.tsx` also has an "Upload your own" mode toggle in the same card — file upload into the `uploads` table/bucket, formerly its own `uploads/` tab, folded in here since Videos' own inline upload made a standalone tab redundant), Videos (`videos/`, image-to-video or pure character-referenced video, with duration/ratio controls sourced from `byteplus/model-limits.ts`, and its own inline "upload a source image" control backed by the same `uploadImage` action), Characters (`characters/`, a single list page — character CRUD, sheet generation, and primary-image/outfit-label picking all happen inline per-card via `character-list.tsx`; there is no separate `characters/[assetId]/` detail route, matching the same inline-card pattern the Scenes Assets tab uses via `scenes/assets-list.tsx`). Shared display components live in `_components/` (`status-pill.tsx`, `generation-media.tsx`, `generation-feed.tsx`, `media-grid.tsx`, `quantity-control.tsx`, `duration-control.tsx`, `ratio-control.tsx`, `resolution-control.tsx`, `prompt-mention-field.tsx`, `zoomable-image.tsx`, `asset-generation-workspace.tsx`) — reuse these rather than re-implementing per tab.

There used to be a separate `storyboard/` tab (script → breakdown → per-shot generation) with `scenes/` as its read-only alias; `storyboard/` is gone. **Scenes** is now the primary breakdown flow, modeled directly on an Assistant Director's scene breakdown sheet rather than a shot list: `generateSceneBreakdown()` (`src/lib/actions/scenes.ts`) populates each scene's own `script_text` (verbatim script excerpt) and `duration_seconds` directly, plus `scene_assets` rows (which characters/locations/props appear in the scene, with a per-character `wardrobe_note`) — no shot rows are created by this flow. `shots`/`shot_assets` and the `kind='shot'` generation path still exist in the schema and are still valid data for old projects, but are **deferred, not deleted**: current UI generates at the scene level (`kind='scene_storyboard'`, one combined multi-panel image per scene) rather than per shot. Don't assume shot-level generation is reachable from the UI without checking `src/app/projects/[id]/scenes/` and `src/lib/actions/scenes.ts` first.

**Character/media references in prompts** are now picked via `@mention` text parsing in the prompt field itself — this replaced an earlier reference-image-picker UI (`character-picker.tsx`'s `CharacterPicker` component still exists but is no longer rendered anywhere; only its `CharacterOption` type is still imported). `_components/prompt-mention-field.tsx`'s `PromptMentionField` opens an inline dropdown when the user types `@` in a prompt textarea (Images and Videos tabs); `extractMentionedAssetIds(prompt, options)` re-derives which ids are referenced by scanning the *submitted* prompt text for `@Name` (case-insensitive, longest-name-first so `@Alex` inside `@Alexander Reed` doesn't also match, word-boundary checked) rather than tracking mention state in a separate array — deleting `@Name` from the prompt text naturally drops that reference with nothing else to keep in sync. `mentionStyle="screenplay"` (Videos tab's dialogue field, prefilled from `scenes.dialogue`) inserts `@NAME` in caps on its own line as a speaker tag instead of the default `mentionStyle="inline"`'s `@Name ` inline. Mentioned ids split into two kinds before the server action call: character/location/prop assets go through `referenceAssetIds` (plural — multiple simultaneous references are supported, not just one) and are resolved server-side, never client-side, by `src/lib/media/asset-references.ts:resolveAssetReferenceUrls()` to each asset's primary `asset_images.storage_path` (or a `referenceImageOverrides`-selected labeled variant, or most-recently-created as a last-resort fallback), freshly re-signed — deliberately not `assets.reference_image_url`, which is itself just a signed URL cached at some earlier generation time with a 1h TTL and never refreshed, the same staleness bug class `generations.storage_path` exists to fix (see Terminal media URLs above). `@`-mentioned uploads/prior-generated images aren't tied to an asset at all, so their storage path is re-signed client-side instead and sent as `extraReferenceImageUrls`, merged server-side with the asset-derived list before the provider call. Video's "turn into video" source-image mode (`handleVideoSubmit` in `image-generate-form.tsx`) reuses the same mention field but only offers uploads/generated images, not characters — BytePlus drops reference images outright whenever a source image is already present, so a character mention there would silently do nothing.

## Project state

Build proceeds in phases (see migration filenames: `phase1_projects`, `phase2_storyboard`, `phase3_generations`, `phase4_video_workflow`, `phase5_media_studio`, `phase6_script_enhance`), followed by a run of unphased migrations layering on top: `scene_storyboard` (scene-level combined storyboard image, see IA section above), `preserve_generations_on_scene_shot_delete` (the cascade→set-null bug fix above), `billing_subscriptions_credits` + `add_subscriptions_realtime` (Stripe billing — see the Billing & credits section above), `shot_asset_links`/`scene_breakdown_sheet`/`asset_image_labels` (the shot→scene breakdown pivot, also above). Video generation (phase 4) uses Vercel Workflow DevKit; the project-scoped media studio (phase 5 — freeform images, character sheets, uploads, BytePlus ModelArk) builds on top of it. Billing/credits (subscriptions + credits_ledger) **is implemented**, not a future phase — check the latest migration and `src/lib/actions/` before assuming a feature is or isn't there rather than trusting phase-name intuition, since real work has moved past the original phase1–6 plan.

**Local env**: `.env.local` has `SUPABASE_SECRET_KEY`, `BYTEPLUS_API_KEY`/`BYTEPLUS_IMAGE_MODEL`/`BYTEPLUS_VIDEO_MODEL`, and `DEEPSEEK_API_KEY` set — so image/video generation runs against the real BytePlus adapters, the LLM provider (script generation/breakdown/enhancement) runs against the real DeepSeek adapter (not mock — DeepSeek wins llm/'s adapter-selection priority over Gateway), and workflows can reach a terminal state. `AI_GATEWAY_API_KEY` is not set, so nothing currently falls through to the Gateway adapter in any of the three capability folders. No `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET` is set, so billing runs on the mock adapter (`subscribe()` activates a subscription synchronously with no external payment step) — keep that in mind when debugging anything that looks like it skipped a real checkout.
